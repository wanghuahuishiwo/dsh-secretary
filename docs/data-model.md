# 底层数据设计

> 本文定义当前领域模块、事实、关联和持久化规则，**不是产品导航或页面结构**。产品模块、入口与共享边界见 [AGENTS.md](../AGENTS.md#产品模块)；产品形态见 [产品需求](prd/README.md)。
> 术语定义见 [glossary.md](glossary.md)。

## 1. 领域模块

| 模块 | 职责 | 是否拥有独立事实 |
|---|---|---|
| GTD | 管理承诺、项目、行动及其可用性。 | 是（Markdown 数据面，见 §2） |
| 时间 | 管理时间计划与时间实录，覆盖工作及全部生活时间。 | 是 |
| **Tag** | 管理标签类型、层级、关联和查询汇总；拥有 `tags` 表。 | **是** |
| Goal | 当前没有 Goal 事实；只有 bundle 级空 GoalService。 | 否；没有 Goal 实体或表 |
| Agent | 承接、协商、准备和跟进，调用上述模块，不另建平行事实。 | 否 |

GTD 和时间不是对全部模块的穷尽。模块、入口和共享边界见 [AGENTS.md](../AGENTS.md#产品模块)；本文只记录事实所有权与依赖。GTD 与时间彼此不互相依赖；未来学习、成长、资产等产品也遵循同一条依赖方向。

**派生视图不是一级产品，而是各模块内部的读取方式**：GTD 内部有 Next Actions、Today、Forecast；Time 内部有计划、实录和深度时间视图；Tag 内部有按层级筛选与汇总的视图。它们共同遵守一条设计原则：从同一事实源即时派生，不另存一份视图数据。统计、预算与对账属于另行专题，不因该原则而自动进入当前范围。

## 2. GTD 事实与边界

GTD 事实存放在插件自有的 Markdown 数据面（`$DSH_HOME/storages/secretary/gtd/`，契约见目录内 README.md）：checkbox 表达行动状态、缩进表达层级、Obsidian 式标签表达属性、标题表达项目；由秘书／普通 agent／用户三方经通用文档工具或 Obsidian 直接读写，现读现写。旧的 SQLite GTD 域（projects / actions / inbox 表）已退役。下述边界与方法论语义不因载体改变。

### 2.1 进入系统的条件

- 能在约两分钟内立即处理的事直接完成，不持久化。
- 只有尚未闭环、需要后续推进或跟踪的承诺才进入 GTD。
- 想法、参考资料与知识沉淀进入知识库，不混入执行型 Inbox。
- 吃饭、睡觉、洗漱等日常活动不进入 GTD，也不生成 Action。

### 2.2 日期语义

| 字段 | 含义 | 关键边界 |
|---|---|---|
| Defer Date | 不早于此时间开始可用 | 不是打算执行的时间 |
| Planned Date | 打算何时开始做 | 是时间点和柔性意图，不是时间区间 |
| Due Date | 必须在此之前完成或放弃 | 不是计划完成时间 |
| Estimated Duration | 预计工作量 | 不是计划区间或实际时长 |
| Completed Date | Action 变为 Completed 的时刻 | 不是实际工作区间 |

不另设「行动计划」概念；Action 上的 Planned Date 已足够表达意图。

### 2.3 Next Actions

- 是当前可选择的 physical, visible next step。
- 可以是不属于项目的独立行动。
- 顺序项目的后续行动受前序阻挡；并行项目可同时有多个 Next Actions。
- 不要求 Planned Date 或时间块。
- 通常按 Context 组织，也可按 Project 查看；这是视图差异，不是两份事实。

## 3. 时间事实与边界

| 概念 | 回答的问题 | 数据特点 |
|---|---|---|
| 时间计划 | 打算如何安排某个具体日期的各时段？ | 由带明确开始、结束时刻的日期计划块组成，可包含睡觉、吃饭、通勤、娱乐和个人发展等活动。 |
| 计划模板 | 哪些周一到周日安排可以复用？ | 独立的周模板功能；可明确应用到指定日期，应用后不与日期计划自动同步。 |
| 时间实录 | 实际时间花在了哪里？ | 由实录块组成，必须有可说明的事实来源。 |

约束：

- 时间计划和时间实录是两条独立序列，实际不从计划自动复制。
- 计划块和实录块都必须且只以时间标签作为分类主体；GTD 对象只能在备注中提及，不与时间块建立直接结构化关联。
- 开始／停止实录不自动完成 Action；完成 Action 不伪造实际区间。
- 目标不是「计划 = 实际 100%」，而是让偏差可见、可解释、可调整。

### 深度时间（精力画像）

- 本产品中精力画像与深度时间指向同一个精力周模板子模块。
- 基础数据是一张 7×24 的周模板表，每小时格为可选枚举：`high` / `medium` / `low` / 未设置，不是布尔值；未设置不表示 `low`，用户可只使用 `high`。
- 当前仅支持持续复用的基础周模板，不支持指定日期的例外模板。
- 深度时间是指导用户安排和 Agent 理解精力分布的独立画像，不从时间实录派生，也不是统计视图。
- 可依据实际执行情况和当时状态动态调整；模块提供原子且输入输出明确的能力，Agent 使用策略由 Skill 决定，不写入领域模型。

## 4. 独立 Tag 模块

### 4.1 数据结构

```ts
interface Tag {
  id: number          // 自增数字主键，系统自动生成
  name: string        // 用户维护的展示名称
  kind: 'time' | 'context' // 系统内置用途类型；新增类型须由产品显式扩展
  parentId?: number   // 标签树父级
  color?: string
  description?: string // 这个标签算什么、什么时候该选它；≤500 字符，空串按未设置处理
}
```

- `kind = time`：用于时间分类与统计。
- `kind = context`：用于 GTD 执行情境。
- `kind` 决定标签语义和允许的关联对象，不是用户自定义的展示分组；未来新增类型必须由产品明确用途和规则。
- 同一棵标签树必须属于同一个 `kind`：创建根标签时确定，子标签继承父标签的 `kind`，禁止跨 `kind` 的父子关系和移动。同名标签可分别存在于不同 `kind` 的树中，但仍是不同 Tag。
- 当前所有 `kind` 共用上述统一字段和管理能力，不引入类型专有状态或属性；差异化生命周期等细节留待后续。
- 标签树只负责组织、筛选和汇总，不改变 Project / Action 的归属关系。
- 用户只维护 `name`、`color` 与 `description`。AI 默认使用 `name` 和上下文；需要精确消歧时，可使用 `tag:12`、`action:345` 这类带类型的短数字引用。
- `description` 写「什么时候选这个标签」的判据，不是名称的复述：名字自带含义的（睡眠、吃饭）可不写，靠约定才成立的（主线／副线、方法论实践）必须写，否则几个月后没人记得当初的分法。`update` 传 `null` 可清空。

### 4.2 任意层级都可关联

父标签和叶子标签都可以被关联，不采用 leaf-only 限制。

直接关联父标签表示「只确定大类，尚未细分」。以后增加子标签，不影响既有直接关联。

### 4.3 只保存实际选择的标签

关联一个标签时，只保存该标签，不把它的祖先标签复制到记录上。

查询父标签时：

```text
直接关联父标签的记录
+ 关联其任意后代标签的记录
→ 按记录去重
```

### 4.4 GTD 时间标签与全层级继承

- 项目段的 `#标签` 对其下所有行动生效；行动行的 `#标签` 是追加，不覆盖或阻断继承。
- 独立行动必须自己带时间标签，才能保证每个行动都有有效时间标签。
- `time` 标签因此可用于 TimeBlock 和 GTD Project／Action；`context` 仍用于 GTD 情境分类。TimeBlock 与 GTD 之间只共享标签，不建立直接结构化关联。

```text
有效 Tags = 自己的 Tags + 所有 GTD 祖先的 Tags（按 Tag id 去重）
```

继承只用于查询，不复制写入子 Action。

这里有两种不同的关系：

- **标签树向上汇总**：子标签的命中结果归入父标签查询。
- **GTD 层级继承**：Project / 父 Action 的标签向子 Action 派生。

## 5. 时间块

计划块与实录块共享活动内容，且**都落在具体日期**。计划模板是独立的复用工具，不替代日期计划。

```ts
interface TimeBlockContent {
  timeTagId: number  // 必填且是唯一分类主体，指向 kind = time 的 Tag
  note?: string      // 可补充说明或提及 GTD 对象，不形成直接结构化关联
}

interface PlanBlock extends TimeBlockContent {
  id: number
  startAt: string                // 带时区的具体开始时刻
  endAt: string                  // 带时区的具体结束时刻
}

interface ActualBlock extends TimeBlockContent {
  id: number
  startAt: string
  endAt?: string                 // 运行中实录尚未结束时缺省
  actualSource: 'user_reported' | 'agent_observed' | 'imported'
  focus?: 'deep' | 'shallow'
}

interface PlanTemplateBlock extends TimeBlockContent {
  id: number
  weekday: number                // 1–7，周一至周日
  startTime: string              // 模板内本地时刻，如 09:00
  endTime: string                // 模板内本地时刻，如 11:30
}
```

- `timeTagId` 回答「这段时间算什么」，是时间块唯一的分类主体。
- 备注可以提及 GTD 对象，但不形成 `gtdRefs` 等直接结构化关联，也不要求睡觉、吃饭、娱乐等生活时间拥有 GTD 对象。
- 计划与实录互不回写；实录可以改做其他事项，不修改具体日期计划。
- 应用计划模板时生成或替换目标日期的计划块；此后模板与日期计划互不回写，小长假可直接调整具体日期。
- 任意时间块都可以重叠，以多个块自然表达并行活动；没有 `dedicated`（专用）类型或互斥限制，也不需额外的并行标记。
- 并行活动使用独立块表达自己的时间标签，例如同一通勤时段同时存在「通勤」和「听 Git 热榜视频」。
- 重叠时间的汇总口径留待统计专题，不在记录模型中通过互斥约束预先限制。

## 6. 持久化、重新加载与坏记录隔离

Secretary 的 GTD、Tag、Time 三个领域都由 [storage domain 包装层](../packages/storage/domain/README.md) 路由到同一个 SQLite 文件。读写在两个层次上工作：

- **领域在 open 时读取一次全量快照**，之后每条写入逐条写回 SQLite；关闭时不整表回写。
- 因此**外部写入**（迁移脚本、修复脚本、其他进程直接改库）不会被运行中的进程察觉，直到该领域重新加载。

### 6.1 重新加载

CLI（`dsh-secretary`）的 `tag reload` 与 `time reload` 关闭当前领域、按同一份 spec 重新打开，让之后的读写落在新快照上。它不重启宿主、不改写任何事实，也不触发领域间的联动。外部改库后必须显式 reload；否则服务继续返回旧值，用旧 id 上色还会把事实写到错误标签上。画布顶部提供同一件事的产品入口：刷新按钮调用 `TimeProductService.reloadWindow`，重读标签与时间块后重画当前窗口。GTD 数据面是 Markdown，现读即所见，无 reload。

### 6.2 坏记录隔离

领域 open 时若某条记录不再匹配 schema，包装层把它移出原表、写进 `secretary_quarantine` 领域并记录 error 日志，然后重试 open；域照常可用，其余记录不受影响。隔离记录保留原值与拒绝原因，供事后核对与修复。没有这一层时，一条历史脏数据会让整个域打不开，并连带让其他域的写入失败（例如 GTD 的标签引用检查会拦住任何标签删除）。
