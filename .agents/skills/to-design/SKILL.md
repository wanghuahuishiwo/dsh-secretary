# to-design

拷问（`grill-with-docs` 或同等对话）结束后调用。把讨论结果**补进**需求 Issue，让 OD 设计 session 只靠这张票就能开工。

## 原则

1. **不重写正文**：先读当前正文和评论，保留用户已写的需求内容；只补缺的部分，不改原有结构、标题和措辞。
2. **不定义需求格式**：需求 Issue 长什么样由它自己决定；本技能只补内容，不引入新模板。
3. **缺什么补什么**：正文需要让设计开工的信息——要做什么、交互约束、引用的设计契约（`DESIGN.md`、`design/<module>/`）、组件边界、验收标准——已有的不重复；评论追加一条，内容为技术相关的决策、结论、待决。
4. **分类穷尽**：列明细就列到穷尽，否则只给类别名；列一半比不列更糟。
5. **评论只追加**：不改写历史评论。
6. **状态**：把需求 Issue 推到 `ready-for-design`；标签先核实存在，缺失就报告，不自动创建，也不拿别的标签代替。
7. 不建 Design Issue，不进 Spec，不实施，不替用户确认。
8. 不写文件路径和代码片段；决定性的类型或状态机形状可以内联，并注明来自讨论。

## 输入

- 当前对话里的拷问结论；
- 需求 Issue（编号或真实 URL）；没有就先建一张 `enhancement` 需求票；
- 项目工单约定：先读 [docs/agents/issue-tracker.md](../../../docs/agents/issue-tracker.md) 和 `.agents/drivers/tracker.md`。

## 完成

返回需求 Issue 的真实链接，并说明：正文补了哪些内容、哪些原文保留未动、评论写了哪几项、标签是否已就位。缺信息的地方标「待确认」，不编造。所有 `gh` 命令显式 `--repo wanghuahuishiwo/dsh-secretary`；写后回读。
