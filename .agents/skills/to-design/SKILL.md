# to-design

拷问（`grill-with-docs` 或同等对话）结束后调用。把已经谈清楚的东西**写回需求 Issue**，让 OD 设计 session 只靠这张票就能开工。

## 输入

- 当前对话里的拷问结论；
- 需求 Issue（编号或真实 URL）。没有就按 `submit-ticket` 建立一张 `enhancement` 需求票，再写回；
- 项目工单约定：先读 [docs/agents/issue-tracker.md](../../../docs/agents/issue-tracker.md) 和 `.agents/drivers/tracker.md`。

## 写回规则

**正文（覆盖写，保留未涉及的原有内容）**

```md
## 需求与设计补充

### 目标
<用户视角：现在什么不好、要变成什么>

### 范围
- 涉及模块：<只列实际涉及的产品模块>
- 不做：<明确排除的相邻工作>

### 设计补充
- 交互约束：<OD 设计必须遵守的交互/布局规则>
- 设计契约：<引用的 DESIGN.md 与 design/<module>/ 资产>
- 组件边界：<哪些共享组件/壳会动，不碰什么>

### 验收标准
- [ ] <可观察结果>
```

**评论（追加一条，三节按状态穷尽）**

```md
## 技术相关的决策、结论、待决

### 决策
- <已决定的技术方案与依据>

### 结论
- <讨论中得出的技术结论>

### 待决
- <留到后续开发流程解决的问题>
```

三节缺内容时写「无」，不删节：已决定、已得出、未定，互斥且穷尽。

**状态标签**：把需求 Issue 推到 `ready-for-design`。标签必须先用 `gh label list` 核实存在；缺失时报告，不自动创建，也不拿别的标签代替。

## 约束

- 分类要么不列明细，要么列到穷尽；列一半比不列更糟。
- 不写文件路径和代码片段；决定性的类型或状态机形状可以内联，并注明来自讨论。
- 不复制 PRD 全文，引用段落即可。
- 不建 Design Issue，不进 Spec，不实施，不替用户确认。
- 所有 `gh` 命令显式 `--repo wanghuahuishiwo/dsh-secretary`；写后回读正文、评论和标签。

## 完成

返回需求 Issue 的真实链接，并说明：正文写了哪些节、评论写了哪三节、标签是否已就位。缺信息的地方标「待确认」，不编造。
