# Ask Wang

你不会记得每一个技能，所以问。

在说明某个技能做什么、或建议跳过某一步之前，先读那个技能的 SKILL.md：这里的摘要只用于定位方向。

**流程（flow）** 是穿过技能的一条路径。大多数路径沿一条**主流程**走，另有两个**入口**汇入这条主流程。其余都是独立的，或是垫在下面的一层词汇。

## 主流程：想法 → 交付

大多数工作走的路线。你有一个想法，想把它做出来。

1. **`/grill-with-docs`** 通过访谈把想法磨清楚。只要你在**一个工作目录**里，就从这里开始：它是有状态的，会把学到的东西留在 `GLOSSARY.md` 和 ADR 里。（没有工作目录？改用 `/grill-me`，见「独立技能」。两者跑同一个 `/grilling` 原语；`grill-with-docs` 是留下文字痕迹的那个，所以只要有 repo 可以留痕，它就是两者中更好的。）
2. **分支：你能在对话里把每个问题都定下来吗？** 如果某个问题需要一个能跑起来的答案（状态、业务逻辑、一个你不得不看的 UI），绕道经过原型，用 **`/handoff`** 双向搭桥（原型住在自己的目录里，这正是 `/handoff` 的用途；见「阶段边界」）：
   - **`/handoff`** 出去，再对着那个文件开一个新会话；
   - **`/prototype`** 用一次性代码回答这个问题；
   - **`/handoff`** 把学到的东西带回，并从原来的想法线程引用它。
3. **分支：这是多会话的构建吗？**
   - **是** → **`/to-spec`**（把对话变成规格），然后 **`/to-tickets`** 把它切成曳光弹工单，每张声明自己的**阻塞边**。然后二选一：
     - **`/implement`** 逐张工单做，**每张之间 `/clear` 上下文**。本地 tracker 上是 `.scratch/<feature>/issues/` 下一张工单一个文件，手动按阻塞优先推进；真实 tracker 上这些边变成原生阻塞链接，所以任何阻塞已完成的工单都可以被领走。每张工单自包含，所以上一张的上下文可以丢弃。
     - **`/implement-spec`** 一次跑完整套规格。它把工单读成一张**任务图**，在就绪的**前沿**上并行跑实现子代理，把一切落到一条**集成分支**。当你想编排这次构建、而不是自己逐张驱动时用它。
   - **否** → 就在这里、在同一个上下文窗口里 **`/implement`**。

   无论哪条路，代码都是靠驱动 **`/tdd`**（一次一个红-绿切片）来构建，并以 **`/code-review`** 收尾——对 diff 的双轴审查（Standards + Spec）。`/implement` 每张工单都跑这两步；`/implement-spec` 的实现者各自驱动 `/tdd`，并对集成分支跑一次 `/code-review`。只想 test-first 构建一个具体行为、不要完整规格时，单独用 **`/tdd`**；想对照某个固定点审一条分支或 PR 时，单独用 **`/code-review`**。

   当工作以 pull request 上交时，**`/pr`** 决定正文：能展示这次改动的最小视图、证明它有效的 before/after 证据、以及一个单向门还是双向门的判断。它是模型可调用的，所以 agent 在写 PR 时随时会去找它。

4. **`/retro`** 闭环。一次构建之后，尤其是一次走了弯路的构建，它回看这段会话，建议改 agent 的**环境**，而不是代码：导航指针、自动化检查、`/code-review` 执行的编码标准、steering 文件、工具。机械性错误变成确定性检查；判断性决定变成编码标准。下一次构建于是从一个更好的环境开始。

### 上下文卫生

把第 1–3 步保持在**同一个不中断的上下文窗口**里（在 `/to-tickets` 之后才 compact 或 clear），这样 grill、spec 和 tickets 都建立在同一份思考上。之后每次 `/implement` 都重新开始，从工单出发。`/retro` 要在它回看的那个会话里跑，在 clear 之前跑；clear 之后，把它指向那个会话的日志。

这里的限制是 **smart zone**：模型仍然保持敏锐的窗口（当前最先进模型上约 150k tokens）。如果会话在 `/to-tickets` 之前逼近它，不要硬撑着在退化状态下继续；在最近的阶段边界 `/compact`，然后继续（见「阶段边界」）。

## 入口

一个会生成工作、然后汇入主流程的起始处境。

- **缺陷和请求在堆积** → **`/triage`**。它让 issue 走 triage 角色并产出 agent-ready 的 issue，之后 **`/implement`** 会接走它们。

  Triage 只用于**不是你创建的** issue：bug 报告、流入的功能请求、任何原始到达的东西。`/to-tickets` 产出的工单已经是 agent-ready 的，所以**不要对它们做 triage**。

- **有东西坏了** → **`/diagnosing-bugs`**。用于难的那些：第一眼看不出所以然的 bug、偶现的 flake、在两个已知良好状态之间悄悄溜进来的回归。在拿到一个**紧密的反馈环**（一条已经对这个 bug 变红的命令）之前，它拒绝先讲理论，然后用回归测试修掉。修好之后，在同一个会话里跑 **`/retro`**，问本来什么能防住这个 bug；如果真正的发现是没有好的接缝能把它锁住，那正是 **`/improve-codebase-architecture`** 的活。

- **一件巨大、模糊的事：一个 greenfield 项目，或一个一次会话装不下的巨大功能** → **`/wayfinder`**，这里认知负担最重的流程。从这里到目的地要怎么走还看不清时，它在 issue tracker 上画一张**共享地图**，由**决策工单**组成，一次解决一个，产出**决策而不是交付物**，直到雾被推回去、路清晰了。`/grill-with-docs` 磨的是一个你在一次会话里握得住的想法，wayfinder 用于你握不住的那个；它更慢也更密，所以只留给恰好这种情况，绝不用于范围清楚的功能。

  地图清晰之后，**它交接，不构建**：在 **`/to-spec`** 处汇入主流程，它把地图里互相链接的决策收敛成一个可构建的计划，然后照常 `/to-tickets` 和 `/implement`。把地图直接循环进 `/implement` 会跳过这次收敛、丢掉链接起来的细节，所以只有当发现这件事确实很小的时候才直接去 `/implement`。

## 代码库健康

不是功能工作，只是维护。

- **`/improve-codebase-architecture`** 在你空出一点时间、想让代码库保持适合 agent 操作时跑。它暴露**加深机会**；挑中一个就_生成一个想法_，你可以把它带进主流程的 `/grill-with-docs`。它是找候选的勘察；**`/codebase-design`**（见下）是在选中的那个上面做设计的工作台。

## 垫在下面的词汇

两个模型可调用的参考，跑在其他技能*之下*，各自是其词汇的唯一权威。当**词**本身而非流程是问题时，直接找它们；或者让上面的技能把它们拉进来。

- **`/domain-modeling`**：磨项目的*领域*语言：挑战模糊术语、解开一个超载的词（「account」同时干三件事）、把难以回退的决定记成 ADR。它是 `/grill-with-docs` 驱动的主动纪律，用来保持 `GLOSSARY.md` 是一份干净的词汇表。
- **`/codebase-design`** 是深模块词汇（module、interface、depth、seam、adapter、leverage、locality），用来设计一个模块的*形状*：在干净的接缝处，用一个小接口包住大量行为。`/tdd` 和 `/improve-codebase-architecture` 都说它。

## 阶段边界

**阶段**是一次会话内的一块工作：grilling、实现、QA。在两个阶段的**边界**上，你有五个选项，而在这整张图里挑哪个是最模糊的决定：

- **继续**：留在原地。不花成本，也不丢东西。
- **`/clear`**：清空窗口，当这里没有任何东西对接下来重要时。
- **`/handoff`** 写一个可携带的 markdown 文件。范围窄：只用于**新 harness**、**新目录**、**同事**，或在**阶段中间**分叉一个支线任务。它买到的是可携带性。
- **子代理**：把一个范围很紧的任务送到它自己的窗口，拿回一份报告。
- **`/compact`** 压缩这段上下文，并用它给一个新会话播种。这是**默认**，在决策树的底部，而不是第一反应。

读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 看那份有序的树：五个问题、每个分支背后的理由，以及为什么一手资料的成本让**继续**成为首先要排除的那个。在边界上做决定；在阶段中间，继续，或者把剩下的拆进子代理。

## 独立技能

完全不在主流程上。

- **`/grill-me`**：和 `/grill-with-docs` 一样凶狠的访谈，但**无状态**：它不在本地保存任何东西，也不建 `GLOSSARY.md`。当你**不在一个工作目录**里时用它（磨一个计划、一个设计、一段写作，任何下面没有 repo 的东西）。如果你在工作目录里，改用 `/grill-with-docs`：它跑同样的访谈还留下文字痕迹，所以严格地更好。
- **`/grilling`** 是访谈原语本身：轮次、前沿、事实是 agent 的活、决定是你的。`/grill-me` 和 `/grill-with-docs` 是两个命名入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 内部都跑它。只有当你想要一个外面没有任何包装的访谈时，才直接找它。
- **`/prototype`** 是一个小的一次性程序，回答一个设计问题：这个状态模型感觉对吗，或者这个 UI 该长什么样。一次性是对代码写法的约束，不是毁灭它的承诺：答案折进真实代码，原型本身作为**一手资料**保留在从 main 切出的 `prototype/<name>` 分支上，由实现 issue 指向它。它是主流程第 2 步的绕道，但任何在纸上难以定下来的设计问题都可以随时找它。
- **`/research`**：把阅读的腿活委托给一个**后台 agent**：它针对**一手来源**调查一个问题，然后在 repo 里留一份带引用的 Markdown 文件。它读的时候你继续工作。它产出的文件是要在 `/grill-with-docs` 处*带进*主流程的，因为研究喂养思考，而不是替代思考。
- **`/to-questionnaire`** 在卡住你的东西既不在你脑子里、也不在代码库里，而在**别人**脑子里时登场，它写一份问卷让那个人填。它是 `/grill-me` 的逆：不访谈你关于主题的看法，而是访谈你关于**发送**的看法（发给谁、你要拿回什么），把问题对准缺口。拿回来的东西是给 `/grill-with-docs` 或 `/to-spec` 的材料。
- **`/wizard`** 用于只有**人**能做的步骤：开通基础设施、配置凭据或 CI secrets、在陌生的第三方后台里点来点去、跑一次性的迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、捕获每个值、把它写进 `.env` 和 GitHub secrets，于是这套流程不再是每次都要重新给 agent 解释一遍的东西。模型可调用，所以 agent 撞到只有你能过的墙时会立刻去找它。如果 agent 自己能做，它就该自己做；这个只用于人真的在环里的地方。
- **`/wait-what`** 是一条没有落到实处的消息的纠正器。在对话中间、在任何其他技能内部使用它，agent 会用你缺的上下文、用平实的语言、用 `GLOSSARY.md` 的词汇重新讲一遍它刚说的话。它事后补救；`/grill-with-docs` 是事前的解药，因为早点约定共同语言，才是阻止行话一开始就到达的原因。
- **`/teach`**：跨多次会话学习一个概念，把当前目录当作有状态的工作区。
- **`/writing-for-agents`** 是写给 agent 消费的文档的参考：skills、AGENTS.md、被指向的文档。
